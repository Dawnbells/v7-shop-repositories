# 订单搜索条件预设设计文档

- **日期**: 2026-06-09
- **模块**: 后端 `v7-shop-services` + 前端 `v7-shop-admin`
- **页面**: 订单管理页、订单审单页
- **状态**: 已评审，待实现

## 1. 背景与目标

订单管理和订单审单页面的搜索条件较多，包括关键词、搜索类型、订单状态、订单类型、重单类型、国家、归属员工、归属部门、平台、下单时间等。当前页面已经把搜索条件同步到 URL query，但用户无法把常用组合保存成命名预设。

目标是让当前登录用户可以保存当前搜索条件并命名，下次在同一页面通过下拉选择快速恢复条件并立即搜索。

核心约束:

1. 预设必须是登录用户个人私有。
2. 预设必须后端落库，支持跨浏览器和跨设备使用。
3. 订单管理页和订单审单页的预设不共用。
4. 本期只覆盖订单管理页和订单审单页，不覆盖订单建联页。

## 2. 已确认需求

1. 用户可以在订单管理页和订单审单页保存当前搜索条件，并输入名称。
2. 保存弹窗包含时间保存方式: 绝对时间、相对时间。
3. 绝对时间保存具体的开始和结束时间。
4. 相对时间保存“相对今天的日期偏移 + 当天时刻”，应用时按当天重新计算。
5. 应用预设后立即恢复搜索条件、回到第 1 页并自动搜索。
6. 预设不保存分页，不保存 `pageNo` 和 `pageSize`。
7. 应用预设时恢复保存时的 `searchType`，并暂时锁定智能推断。
8. 允许保存空条件，但名称必填。
9. 同一个登录用户、同一个页面内预设名称唯一。
10. 同名保存时提示是否覆盖。
11. 支持新增、覆盖、删除，不单独做重命名。
12. 预设列表按最近使用时间倒序，其次按创建时间倒序。

## 3. 现状与约束

- `OrderAudit.vue` 通过 `<order-manager :is-audit="true" />` 复用 `OrderManager.vue`。
- `OrderContact.vue` 通过 `<order-manager :is-contact="true" />` 复用 `OrderManager.vue`，但本期不接入预设入口。
- 搜索表单封装在 `v7-shop-admin/src/views/order/vabAutoComponents/OrderQueryParamLayout.vue`。
- `OrderManager.vue` 已经负责把 `queryForm` 写入 URL query，并从 URL query 初始化搜索条件。
- 审单页默认时间是昨天 09:00 到今天 09:00。
- 后端订单查询使用 `QueryOrderRequest` 和 `/orders/page`。
- 现有 `DynamicConfig` 偏公司和部门配置，不适合承载个人搜索预设。
- 数据实体已有 `company_id` 租户隔离和 `owner/user_id` 归属用户模式，可以复用个人数据归属语义。

## 4. 方案选择

采用新表加查询条件 JSON 的方案。

备选方案比较:

| 方案 | 说明 | 取舍 |
|---|---|---|
| 新表 + 查询条件 JSON | 新增 `t_order_search_presets`，保存用户、页面、名称、时间模式和搜索条件 JSON | 推荐。贴合个人预设，字段变化时不必频繁改表 |
| 复用 `DynamicConfig` | 把用户预设塞进动态配置 JSON | 少建表，但唯一性、最近使用、单项删除都别扭 |
| 每个查询字段拆列保存 | 表里单独保存 `search_type`、`keywords`、`order_status` 等 | 数据库可读性强，但筛选字段变化时维护成本高 |

## 5. 后端设计

### 5.1 数据表

新增表 `t_order_search_presets`，作为登录用户个人数据。

核心字段:

| 字段 | 类型语义 | 说明 |
|---|---|---|
| `id` | Long | 主键 |
| `company_id` | Long | 租户隔离 |
| `user_id` | Long | 预设所属用户 |
| `page_type` | String 或 enum | `ORDER_MANAGER`、`ORDER_AUDIT` |
| `name` | String | 预设名称 |
| `time_mode` | String 或 enum | `ABSOLUTE`、`RELATIVE` |
| `query_params` | JSON | 搜索条件快照，不包含分页 |
| `last_used_time` | LocalDateTime | 最近使用时间 |
| `status` | StatusEnum | 软删除状态 |
| `create_time` | LocalDateTime | 创建时间 |
| `update_time` | LocalDateTime | 更新时间 |

唯一性规则:

同一个 `company_id + user_id + page_type + name` 下，未删除预设不允许重复。

如果数据库唯一索引无法直接表达“未删除状态下唯一”，实现时由后端服务层做兜底校验，保存同名时走覆盖更新。

### 5.2 页面类型

定义页面类型:

```text
ORDER_MANAGER - 订单管理页
ORDER_AUDIT   - 订单审单页
```

不定义 `ORDER_CONTACT`，避免本期功能扩到订单建联页。

### 5.3 时间模式

定义时间保存方式:

```text
ABSOLUTE - 绝对时间
RELATIVE - 相对时间
```

`time_mode` 是保存时用户选择的模式。实际时间转换数据存放在 `query_params.dateRange` 或约定的时间结构中。

### 5.4 接口

接口按个人工具处理，只要求登录，不新增后台菜单权限。所有接口必须强制限定当前登录用户，不允许通过参数操作其他用户预设。

#### 查询预设列表

```text
GET /order-search-presets?pageType=ORDER_AUDIT
```

返回当前登录用户、当前页面类型的预设列表。

排序:

1. `lastUsedTime desc`
2. `createTime desc`

`lastUsedTime` 为空的预设排在已使用预设之后。

#### 保存或覆盖预设

```text
POST /order-search-presets
```

请求核心字段:

```json
{
  "pageType": "ORDER_AUDIT",
  "name": "每日审单",
  "timeMode": "RELATIVE",
  "queryParams": {}
}
```

后端行为:

1. 校验名称非空，长度合理。
2. 校验 `pageType` 只允许 `ORDER_MANAGER` 或 `ORDER_AUDIT`。
3. 校验 `timeMode` 只允许 `ABSOLUTE` 或 `RELATIVE`。
4. 若当前用户当前页面已有同名未删除预设，则覆盖更新该记录。
5. 否则新增记录，并设置 owner 为当前登录用户。
6. 保存时不接受前端传入的 `userId` 或 `companyId` 作为归属依据。

#### 删除预设

```text
DELETE /order-search-presets/{id}
```

只允许删除当前登录用户自己的预设。删除使用软删除。

#### 使用预设

```text
POST /order-search-presets/{id}/use
```

后端行为:

1. 校验预设存在且属于当前登录用户。
2. 更新 `lastUsedTime` 为当前时间。
3. 返回预设内容。

前端选择预设时调用该接口，确保最近使用排序稳定。

## 6. 前端设计

### 6.1 入口位置

入口放在搜索栏右侧，形成同一组搜索相关操作:

```text
[搜索类型 + 关键词输入框] [搜索] [已保存条件下拉] [保存当前条件]
```

不放在批量操作按钮区，因为批量操作区属于订单动作，搜索预设属于筛选条件管理。

### 6.2 保存当前条件

点击“保存当前条件”后弹出弹窗。

弹窗字段:

1. 名称
2. 时间保存方式: 绝对时间、相对时间

前端校验:

1. 名称必填。
2. 名称长度建议 1 到 50 个字符。
3. 允许保存空搜索条件。

同名处理:

1. 前端根据已加载列表先判断同名。
2. 如果同一页面已有同名预设，提示用户是否覆盖。
3. 用户确认后提交保存。
4. 后端仍做同名覆盖兜底，避免并发重复。

### 6.3 已保存条件下拉

下拉只展示当前页面类型的预设:

- 订单管理页展示 `ORDER_MANAGER`。
- 订单审单页展示 `ORDER_AUDIT`。
- 订单建联页不显示入口。

选择预设后:

1. 调用使用预设接口，刷新 `lastUsedTime`。
2. 解析预设中的 `queryParams`。
3. 还原当前支持的搜索字段。
4. 忽略未知字段。
5. 设置 `pageNo = 1`。
6. `pageSize` 保持当前页面值。
7. 同步 URL query。
8. 立即执行搜索。
9. 刷新预设下拉排序。

下拉项提供删除入口，删除前确认，删除后刷新列表。

### 6.4 智能推断处理

当前搜索框有智能推断搜索类型逻辑。应用预设时必须恢复保存时的 `searchType`，并暂时锁定智能推断，避免关键词被重新推断成其他类型。

例如保存时:

```text
keywords = "abc def"
searchType = NAME
```

应用时必须仍按 `NAME` 查询，不能被推断为 `PRODUCT_TITLE`。

## 7. 搜索条件快照

预设保存的是当前搜索条件快照，不保存页面上下文字段和分页字段。

保存字段包括当前支持的搜索项:

- `searchType`
- `keywords`
- `orderStatus`
- `botOrderStatus`
- `repeatType`
- `countryId`
- `platform`
- `dateRange`
- `belongEmployeeIds`
- `belongDepartmentIds`
- `contacted`

不保存字段:

- `pageNo`
- `pageSize`
- `isAudit`
- `isContact`

`isAudit` 和 `isContact` 由页面上下文决定，不写入预设，避免预设串页。

## 8. 时间规则

### 8.1 绝对时间

保存时如果选择绝对时间，直接保存当前 `dateRange` 的两个具体时间。

示例:

```text
保存日: 2026-06-09
dateRange: 2026-06-08 09:00:00 到 2026-06-09 09:00:00
```

下次应用时仍恢复:

```text
2026-06-08 09:00:00 到 2026-06-09 09:00:00
```

### 8.2 相对时间

保存时如果选择相对时间，保存“相对今天的日期偏移 + 当天时刻”。

示例:

```text
保存日: 2026-06-09
dateRange: 2026-06-08 09:00:00 到 2026-06-09 09:00:00
```

保存结构语义:

```text
开始: dayOffset = -1, time = 09:00:00
结束: dayOffset = 0, time = 09:00:00
```

如果在 2026-06-10 应用该预设，则恢复:

```text
2026-06-09 09:00:00 到 2026-06-10 09:00:00
```

### 8.3 时间边界

1. 如果保存时没有 `dateRange`，预设里不保存时间，应用时保持无时间条件。
2. 如果 `dateRange` 不完整，则按无时间处理。
3. 相对时间只处理开始和结束两端都存在的时间。
4. 应用预设后 `pageNo` 固定为 1，`pageSize` 保持当前值。

## 9. 错误处理

| 场景 | 处理 |
|---|---|
| 名称为空 | 前端拦截，提示“请输入条件名称” |
| 名称过长 | 前端拦截，后端兜底 |
| 同名冲突 | 前端提示覆盖，后端保存时覆盖同名记录 |
| 删除不存在的预设 | 后端返回参数错误，前端提示删除失败 |
| 删除不属于当前用户的预设 | 后端拒绝，前端提示删除失败 |
| 使用不属于当前用户的预设 | 后端拒绝，前端提示应用失败 |
| 预设 JSON 有未知字段 | 前端忽略未知字段 |
| 远程下拉项回显失败 | 保留 ID 值，用户可手动清除 |

## 10. 测试与验证

### 10.1 后端测试

覆盖以下场景:

1. 同一用户、同一页面、同名保存会覆盖。
2. 同一用户、不同页面、同名预设可并存。
3. 不同用户、同一页面、同名预设可并存。
4. 查询列表只返回当前用户当前页面预设。
5. 删除只能删除当前用户自己的预设。
6. 使用预设会更新 `lastUsedTime`。
7. 列表排序按 `lastUsedTime desc, createTime desc`。
8. 不合法 `pageType` 或 `timeMode` 被拒绝。

### 10.2 前端验证

覆盖以下场景:

1. 保存绝对时间预设，应用后恢复同一组具体时间。
2. 保存相对时间预设，跨天应用后按当天滚动。
3. 应用预设后自动搜索，并回到第 1 页。
4. 应用预设后 `pageSize` 保持当前值。
5. 应用预设后搜索类型不会被智能推断覆盖。
6. 同名保存提示覆盖。
7. 删除预设后下拉列表刷新。
8. 订单管理页和订单审单页预设互相不可见。
9. 订单建联页不显示保存条件入口。

## 11. 范围外

本期不做:

1. 团队共享预设。
2. 公司级或部门级预设。
3. 预设重命名。
4. 拖拽排序或手动排序。
5. 订单建联页预设。
6. 把预设同步到 URL 之外的其他页面状态系统。

## 12. 实现注意事项

1. 后端不能信任前端传入的用户归属字段，必须使用当前登录用户。
2. 查询、使用、删除都必须限定当前登录用户和当前租户。
3. `query_params` 应只保存搜索条件快照，不保存分页和页面上下文。
4. 相对时间转换在前端完成，后端只保存转换后的 JSON；应用时由前端生成 `Date` 对象。
5. 应用预设时要避免触发关键词 watcher 把 `searchType` 重新推断。
6. 前端恢复远程下拉字段时复用已有回显逻辑。
